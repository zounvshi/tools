## 一、改动方案与数据流

### 1.1 核心结论（先说结论）
现有系统**没有真正的权限与持久化**：登录只是本地 `sessionStorage` 标记，所有「上架/删除/改说明」只写 `localStorage`，从不回写任何存储，需人工「导出新配置」再覆盖仓库。本次重构用 **Pages Functions 作为真实鉴权与写入网关**，把提交/审批/删除全部落到 **Cloudflare R2**（已开通），并用 **Functions 实时读取（no-store）** 解决审批后的「实时可见」与缓存失效问题。运行时**不碰 GitHub 写接口、不需要任何 GitHub 令牌**。

### 1.2 数据流（文字版架构图）

```
浏览器(index.html)
   │  GET /api/tools        (公开；实时合并 原始+新增)
   │  GET /api/pending      (仅管理员)
   │  POST /api/login  /api/submit  /api/admin
   ▼
Cloudflare Pages Functions (functions/api/*)
   │  校验 HS256 令牌(AUTH_SECRET)；管理员动作需 role=admin
   │  读取：原始工具 = 实时 GET GitHub 公开 raw（只读，不写回）
   │        新增工具 = 读 R2 桶 data/tools.json、待审 = data/pending.json（ETag 乐观锁）
   │  写入：仅新增/审批/删除 写 R2 桶(TOOLS_BUCKET)；文件 PUT 到 tools/<id>-<名>
   │  GitHub 原始数据另缓存到 R2 data/base.json 用于宕机兜底
   ▼
Cloudflare R2 桶(TOOLS_BUCKET)
   data/tools.json    (仅「新增/已审」工具, status=approved)  ← 不含原始 8 个
   data/pending.json  (待审核, status=pending)
   data/base.json     (GitHub 原始数据缓存，仅兜底用)
   tools/<id>-<名>    (真实 exe/压缩包)
   （原始 8 个工具：始终来自 GitHub 公开 raw，只读，从不写入 R2/GitHub）
```

- **前台只读**：`/api/tools` 每次**实时合并**「GitHub 原始工具（只读）+ R2 新增已审工具」，响应头 `no-store`，前端 `fetch(..., {cache:'no-store'})` —— 审批通过后**任何用户刷新即见**，规避 CDN/浏览器缓存。
- **服务端兜底**：`/api/tools` 始终从 GitHub 公开 raw 读取原始工具（只读）；若 GitHub 暂不可达，自动回退到 R2 缓存的 `data/base.json`，原数据不会丢；若连缓存也没有，则至少返回 R2 中已新增的数据，页面不崩。
- **提交链路**：用户提交 → 写 `data/pending.json`（`status=pending`）→ 仅管理员在「管理后台」可见。
- **审批链路**：管理员「通过」→ 该条从 `data/pending.json` 删除并追加进 `data/tools.json` → 所有人实时可见；「驳回」→ 仅从 `data/pending.json` 删除。
- **前端兜底**：若 Functions 整体不可用，前端再回退读取仓库根静态 `./tools.json`（只读快照，页面不崩）。

### 1.3 权限矩阵

| 角色 | 判定来源 | 提交新工具 | 删除 | 审批(通过/驳回) | 编辑说明/关于 |
|---|---|---|---|---|---|
| 游客 | 未登录 | 否（引导登录） | 否 | 否 | 否 |
| 普通用户 | 登录(用户名+可选通行码) | ✅ 进 `pending` | 否 | 否 | 否 |
| 管理员 | 登录且命中 `ADMIN_CREDENTIALS` | ✅ 直接上线 | ✅ | ✅ | ✅ |

### 1.4 鉴权拦截点与未授权提示
- **前端拦截**：`requireAuth(role)` —— 未登录弹登录框 + Toast「请先登录」；非管理员 Toast「需要管理员权限」并拒绝打开后台/删除。
- **后端拦截（真正生效点）**：`functions/api/_shared/auth.js` 的 `requireRole(request, env, 'admin')`，任何特权接口（pending/submit/admin）都先校验令牌签名与角色，无效返回 `401/403`。**前端可绕过，但后端不可绕过**——这是安全边界。

### 1.5 管理员名单如何配置（可落地）
通过 Cloudflare 环境变量 `ADMIN_CREDENTIALS`（JSON 数组），例如：
```json
[{"user":"admin","hash":"<sha256(密钥)>"},{"user":"liyt","hash":"<sha256(密钥)>"}]
```
- 支持 `hash`（推荐，存 sha256，不在仓库明文暴露）或 `pass`（明文，仅内网临时用）。
- **向后兼容**：若未配 `ADMIN_CREDENTIALS` 但保留旧 `ADMIN_PASSWORD`，自动视为单管理员 `admin`。
- 普通用户通行码：`USER_PASSCODE`（可选）。配置后用户登录需填；不配则任意用户名即可登录（仅用于署名，弱身份，适合内网）。

### 1.6 令牌/密钥存放与轮换
- **签名密钥** `AUTH_SECRET`：存 Cloudflare 环境变量（非仓库）。令牌 = `base64url(header).base64url(payload).HMAC_SHA256(base64url(...), AUTH_SECRET)`，payload 含 `{sub, role, exp(12h)}`。
- **轮换**：在 Cloudflare 修改 `AUTH_SECRET` 即生效，旧令牌签名立刻校验失败（强制重新登录）。建议定期轮换。
- **GitHub 写入令牌** `GITHUB_TOKEN`：**本方案已不再需要**。数据全部存 R2，运行时仅只读拉取公开 raw 地址用于首次迁移，无需任何 GitHub 令牌；代码推送用 GitHub Desktop（你的账号）即可。

### 1.7 缓存失效策略（对应需求 5）
三层共同保证实时：① Functions 响应 `Cache-Control: no-store`；② 前端 `fetch` 显式 `cache:'no-store'`；③ `_headers` 对静态 `tools.json/pending.json` 设 `no-store` 兜底。审批后前端主动重新拉取 `/api/tools` 与 `/api/pending`，无需等 CDN 过期。

## 四、R2 数据存储与审批链路兼容说明

### 4.1 字段向后兼容（不得破坏线上数据）
- 旧 `tools.json` 的每条工具**无** `status` 等字段。新代码在读取时统一：缺失 `status` → 视为 `'approved'`（`tools.js`、`index.html` 均如此处理）。因此**未改动的旧数据立即可用**。
- 本次交付的 `tools.json` 已用**线上真实的 8 条工具**作为种子（直接抓取自旧站点），可直接覆盖仓库；即便不覆盖，运行时也会**直接从 GitHub 公开 raw 实时读取**原始工具（只读，绝不写回）。

### 4.2 `pending.json`（新增）
- 初始 `[]`。`submit.js` 写入数组；`pending.js` 读取兼容数组与 `{pending:[]}` 两种形态。R2 中路径为 `data/pending.json`。

### 4.3 审批链路写入（ETag 乐观锁）
- 所有写操作先 `GET` 对象拿到 `ETag`，再 `PUT` 带 `onlyIf: {etagMatches}`（已存在时）或 `onlyIf: {etagDoesNotMatch:'*'}`（首次创建时），并发冲突时**自动重试最多 5 次**，避免覆盖丢数据（Cloudflare R2 写后强一致）。
- 「通过」顺序：先写 `data/tools.json`（上线），再清 `data/pending.json`；若第一步成功、第二步失败，可重试，不会数据分裂。

### 4.4 兜底兼容
- **服务端兜底**：`/api/tools` 始终从 GitHub 公开 raw 读取原始工具（只读）；R2 中尚无 `data/tools.json`（还没有任何新增）时，返回的就是「原始工具 + 空新增」；若 GitHub 暂不可达，回退到 R2 缓存 `data/base.json`；若连缓存也没有，至少返回 R2 新增数据，页面不崩。
- **前端兜底**：若 Functions 整体不可用，前端再回退读仓库根静态 `./tools.json`（只读快照，无审批/删除能力），页面不崩。

### 4.5 关于「首次迁移」（已废弃）
- 旧版的「导入旧数据 / migrate」逻辑**已废弃**。新架构下原始工具始终从 GitHub 公开 raw 实时读取，**不需要也不应该**把旧数据搬进 R2。`functions/api/migrate.js` 现为兼容空操作（调用它什么都不搬运，直接返回提示）。若确认不再需要，可删除该文件。

## 五、Cloudflare Pages 部署与回滚步骤

### 5.1 部署前置（一次性）
1. 在 Cloudflare 仪表盘 → 该 Pages 项目 → **Settings → Functions → R2 bucket bindings** 添加绑定：变量名 **`TOOLS_BUCKET`**，选你建的 R2 桶。
2. 同一项目 → **Settings → Environment variables** 添加以下变量：
   - `AUTH_SECRET`（随机长字符串，已为你生成，见《部署配置.txt》第【1】行）
   - `ADMIN_CREDENTIALS`（JSON，见 1.5；强烈建议用 `hash`，用 `gen-admin.html` 生成）
   - `R2_PUBLIC_BASE`（R2 桶开启 Public Development URL 后的公开网址，结尾不带 `/`）
   - `MAX_UPLOAD_MB`（单个上传上限，默认 `100`）
   - `USER_PASSCODE`（可选；不配则用户登录免通行码）
   - `MIGRATE_SOURCE_URL`（可选；默认线上旧地址，部署到自有仓库时才改）
3. 确认「Build command」留空、「Build output directory」为仓库根（本项目无构建）。

### 5.2 部署
- 本仓库已连接 GitHub：**用 GitHub Desktop 把交付目录的文件覆盖提交到 `main` 分支并 push** 即触发自动部署（GitHub Desktop 用你自己的账号登录，无需手动令牌）。
- 或本地用 Wrangler：`npx wrangler pages deploy . --project-name=<你的项目名>`（需先 `wrangler login`）。

### 5.3 首次上线 + 回滚
- **首次上线**：部署后即可用——原工具直接从 GitHub 读取显示，无需任何导入操作（详见《部署步骤.md》第五步）。
- **代码回滚**：Cloudflare Pages 控制台 → **Deployments** → 选上一个正常版本 → **Rollback** 一键回滚；或 Git 侧 `git revert` 后 push。
- **数据回滚**：数据在 R2，可进 R2 桶手动删除 `data/tools.json` / `data/pending.json`（即清除所有「新增」数据，不影响 GitHub 原始）；原始工具始终从 GitHub 读取，无需回滚。

## 七、前端鉴权方案的局限（必读，对应需求 2 的「标注其局限」）

- **静态站点无服务端会话**：令牌与前端的 `requireAuth` 逻辑都在浏览器，可被绕过；**真正的防线是后端 `requireRole`**（令牌签名 + 角色校验），普通用户无法伪造管理员令牌（不知道 `AUTH_SECRET`）。
- **令牌存 `localStorage`**：存在 XSS 泄露风险（任何站内 XSS 可窃取令牌）。缓解：站点内容可信、保持 CSP；密钥 `AUTH_SECRET` 泄露则需轮换。
- **用户身份弱**：普通用户登录仅用于署名，`USER_PASSCODE` 若省略则任意用户名可登录——适合内网可信环境，不适用于公网强认证。
- **GitHub 令牌已不再需要**：运行时仅只读拉取公开 raw 地址用于显示原始工具，**从不写入 GitHub**，无写令牌、无单点泄露风险。代码推送走 GitHub Desktop（你的账号），不交手动令牌。
- **R2 桶绑定名写死**：代码里 `TOOLS_BUCKET` 是固定绑定名，Cloudflare 后台绑定必须一字不差叫这个，否则找不到桶（会返回 500，已写入前端错误提示）。
- **结论**：这是「内网部门工具平台」级别的合理方案；若未来要上公网强权限，应迁移到 GitHub OAuth / Cloudflare Access 等真身份认证，并给 R2 桶开启更严格的访问策略。
